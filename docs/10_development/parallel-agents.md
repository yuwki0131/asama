## 背景: なぜ並列化するか

MVP完成・アセットパイプライン成熟という節目に対し、残作業は次の4軸に整理できる。

- **A. ビジュアル完成**: ペインタリー移行の全面適用、ユニットアニメ、天守Blender化
- **B. ゲームプレイ深化**: MVPから繰り延べた項目の回収(兵種相性・高低差・射線・攻撃側兵糧・鉄砲/騎兵)
- **C. コンテンツ多様化**: AIプロファイル追加、シナリオ複数化
- **D. 技術基盤**: 巨大単一ファイルの分割、UI層テスト

これらを直列で進めると時間がかかるため、担当領域を排他的に分けた
**5エージェント並列体制**で進める。D(技術基盤)は独立エージェントとせず、
各エージェントが自領域のリファクタリングを最初のタスクとして持つ。

## 実行者モデル

- **フォアグラウンド**: アートA/B+統括は**メインセッション(統括エージェント)**が持つ。
  アートの判定はユーザーとの対話式(小出しリテイク前提)であり、この直列性は不可避のため
  セッションの主戦場とする。1往復に複数の判定案件を載せて往復回数を圧縮する。
- **バックグラウンド**: sim / UI / コンテンツは**機械ゲート(typecheck・test・監査)で
  自走可能**なため、統括が codex exec を別クローン・別ブランチでバックグラウンド起動し、
  ユーザーの判定待ち時間と並行して走らせる。統括は毎ターン裏レーンを回収・PR統合する。
- 将来、持続性が必要になったら(日をまたぐ自走等)ユーザー運転の別セッション or
  定期実行へ昇格する(クローン+PR設計は実行者非依存のため移行コストなし)。

## 基本原則

1. **所有ディレクトリの排他**: 各エージェントは自分の所有ディレクトリのみ変更する。
   所有権外の変更が必要な場合はコードを書かず、所有エージェントへ依頼書を出す
   (→ 後述の requests 規約)。
2. **リファクタリングは自領域で**: 巨大ファイルの分割等は、その領域の所有エージェント自身が
   行う。他人の領域をリファクタリングしない。
3. **アートディレクションは中央集権**: `docs/05_map-and-art/art-direction.md` は分割せず
   共有の憲法とする。変更はユーザー承認ゲート(実レンダー選定ゲート方式)経由のみ。
   判定は当面対話式: 型が確立するまではスケール化(バッチ判定等)を行わず、
   1件ずつ画像を提示して対話で判定する。
4. **ペイントオーバー標準工程の共有**: 「3D構図(supersample 8)→codex image_gen
   ペイントオーバー(構図・光・トーン厳守)→取り込みゲート(トーン較正+元レンダーの
   アルファでマスク)」がアートA/B共通の標準工程。取り込みツール(`aiIntake.ts`)と
   `assets/definitions/ai-intake.json` はアートA所有、`assets/source/ai/` の原画は
   担当アセットごとにファイル名で排他(generated PNGと同じ規約)。

## 統括(オーケストレーション)

5エージェントはいずれも対等なワーカーであり、全体統括は行わない
(UI/基盤エージェントも `apps/game` 担当のワーカーの1人であって統括役ではない)。

統括は**ユーザー+メインセッション**が統合用ワークスペース(main保持)で兼ねる。
専任エージェントは置かない(マージ判断・アート承認・スコープ裁定はユーザー判断が
必須のため、専任化しても待ち合わせが増えるだけ)。統括の役割:

- PRのレビュー・マージ判断、マージ後の整合確認(manifest再生成等)
- バックログの維持と各エージェントへのタスク払い出し
- requests/ の裁定(所有権をまたぐ変更の交通整理、優先度の衝突解決)
- アート承認ゲート(実レンダー選定方式)の運営
- 確定仕様の `docs/` への昇格

## アートA / アートB の境界

分割基準: **タイルとして敷き詰めて接続されるものはA、単体で配置されるものはB**。

リテイクの発生源が異なることが2分割の理由。建築・地形系のリテイクはアライメント・接続の
技術的問題、ユニット・植生系のリテイクは様式・ルックの審美的問題であり、修正ループが
互いに独立している。「新規制作 vs リテイク」のような作業種別での分割は同一ファイルを
取り合うため採用しない。

### アートA: 建築・地形(ハードサーフェス / ピクセル契約系)

- 建物(蔵・市場・兵舎・武家屋敷・町区画・櫓・天守・本丸)
- 城郭(塀・柵・門・石垣・土塁)と接続16マスクキット、斜め壁・円弧壁等のカーブ語彙
- **地形タイル**(grass/dirt/stone/water の base・接続マスク・マクロタイル)
- 道路、空堀・水堀、土橋・木橋、農地、地形境界トランジション
- Blender共通基盤(カメラリグ・ピクセル契約・マテリアル・レンダー設定)の唯一の変更権者。
  キャリブレーション検証(`assets:blender:calibration`)の責任者を兼ねる

### アートB: ユニット・植生(有機物 / 様式表現系)

- ユニットスプライト全種(足軽・弓・工兵、および新兵種: 鉄砲・騎兵・補給荷車)と
  4方向アニメーション
- 植生 `deco-*`(松・杉・広葉樹・竹・葦・茂み・雑草)— 様式主義
  (狩野派・琳派・大和絵の様式語彙)の適用
- 無機物の装飾(岩 `rock-cluster` 等)もデフォルトでB(接続契約がないため)

## ワークスペースとGit運用フロー

### ワークスペース: 1エージェント = 1クローン(完全分離)

```
~/workspace/asama          # 統合用(ユーザー+統括メインセッション、main を保持)
~/workspace/asama-art-a    # branch: agent/art-a
~/workspace/asama-art-b    # branch: agent/art-b
~/workspace/asama-sim      # branch: agent/sim
~/workspace/asama-content  # branch: agent/content
~/workspace/asama-ui       # branch: agent/ui
```

- git worktree ではなくフルクローンを採用。`.git` ×6 のディスクコストと引き換えに
  完全分離が得られ、クラウドエージェント(Copilot等)と同じ動作モデルになる。
- pnpm はグローバルストア共有のため `node_modules` の実コストは小さい。
- Blenderレンダーキャッシュ(`assets/intermediate/`、gitignore済)はアートA/Bの
  ワークスペースのみ構築すればよい。他エージェントはレンダー不要
  (生成PNGはコミット済みのため pull で受領)。

### フロー: ブランチ → PR → CI → main

1. 各エージェントは自ブランチに vYYMMDDHHMM スナップショットコミットを継続
2. **1日1回以上 push → PR 作成**(溜めない。並列化の失敗パターンはほぼ「長期ブランチの巨大マージ」)
3. CI(GitHub Actions: verify + e2e)がマージゲートを検証
4. マージ後、他エージェントは作業開始時に必ず main を自ブランチへ取り込む
5. PRベースにすることで Copilot レビュー / Codex 委任との接続も自然になる

マージ方式は merge commit(スナップショット履歴文化を保つ)。

### マージゲート(統合前に必ず通すチェック)

| チェック | 対象 |
|---|---|
| `pnpm run typecheck` | 全エージェント |
| `pnpm test` | 全エージェント |
| `pnpm run assets:audit:production` | アートA/B(candidate ゼロ要求) |
| `pnpm run assets:lint:art` | アートA/B(art-rulebook 機械検査) |
| `pnpm run assets:blender:calibration` | アートA(共通基盤変更時) |

いずれもBlender実行なしでCI可能(監査はコミット済みPNGと定義の検査)。

### バイナリアセットの扱い

- `public/assets/generated/` と `assets/definitions/` へのコミットは**アートA/Bのみ**。
  `.git` 肥大の主因はPNG churn のため、コミット権を限定して抑制する。
- 担当アセットのファイル名がA/Bで重ならないため、PNG単位で排他になる。
- `manifest.json` 等の生成物はコンフリクトしてもマージせず、統合後に `assets:all` で再生成
  (キャッシュ差分レンダーのため安価)。
- **Git LFSは採用しない**: publicリポジトリではLFS帯域(無料1GiB/月)が
  第三者のcloneでもオーナー負担で消費されるため、バイナリは素のgitで持つ。
  決定論レンダーにより内容不変のPNGはバイト一致(=コミット差分ゼロ)なので、
  ルック確定後のchurnは自然に収束する。

### 所有権違反の禁止(実例あり)

**所有権外のファイルに必要な変更(型フィールド追加等)が生じても、自前実装は禁止。**
requests/ に依頼書を書き、所有エージェントの実装を待つ(または統括が裁定)。
実例: UIエージェントが nextWaveTick を shared に自前追加→simの正式実装とコンフリクト。
レーン指示文には毎回この禁止事項を明記すること。

### エージェント間連携: requests/ 規約

- ディレクトリ: `requests/<from>2<to>/`(例: `requests/content2sim/`、`requests/ui2sim/`)
- 依頼書: `YYYY-MM-DD-<テーマ>.md` — 目的・受け入れ条件・関連仕様を記載
- 完了報告: `YYYY-MM-DD-<テーマ>-ready.md` — 実施内容・実行コマンド・検証結果・残件
- `packages/shared` の型変更はシミュレーションエージェントが変更通知を書く

### 環境の分離

- 複数ワークスペースで同時に `pnpm run dev` するとポート衝突するため、
  ワークスペースごとにポートをずらす(env 等で設定)
- `saves/` は各クローンでローカルに分離(意図通り)
- リポジトリ(github.com:yuwki0131/asama)は**パブリック**。
  確定事項の「ローカル実行・インターネット非公開」は**ゲームを公開デプロイしない**という
  意味であり、リポジトリの可視性とは別の話。
